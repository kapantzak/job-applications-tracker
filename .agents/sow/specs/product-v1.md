# Product Contracts: v1 (intended)

Status: reconciled with shipped v1 behavior on 2026-11-06 (SOW-0001 close). The design document remains the narrative; this file lists the contracts other work must not break.

Source of truth for the full design: `docs/superpowers/specs/2026-11-05-job-applications-tracker-design.md`. This spec lists the contracts that other work must not break.

## Runtime

- Package `job-applications-tracker`, binary `jobtrack`, Node >= 22, ESM.
- Server binds `127.0.0.1` only, default port 4173, falls back to the next free port (up to 10 attempts).
- Data directory `~/.job-applications-tracker/` (override `--data-dir`, `JOBTRACK_DATA_DIR`) holding `data.db` and `runs/`.
- No authentication on the local API; documented in README. The API guard rejects requests whose `Host` is not `127.0.0.1`, `localhost` or `[::1]`, rejects state-changing requests with a foreign `Origin`, and requires `Content-Type: application/json` on JSON bodies (415 otherwise).
- All entity ids are UUID strings generated by the repositories. There is no `config.json`; `port` and every other setting live in the `settings` table.

## Profiles (SOW-0014)

- The user keeps any number of search profiles in the `profiles` table (UUID id, required `name` unique ignoring ASCII case, a unique `slug`, plus target roles, locations, remote, seniority, keywords, excluded companies, notes). Settings are shared by every profile.
- Names (SOW-0015): letters and digits of any script with single spaces between words (combining marks may follow a letter or digit, as Indic scripts need), at most 80 characters counted as code points, NFC-normalized and trimmed before the check (`src/server/domain/profile-name.ts`, shared with the UI). Anything else is 400 "name: Use only letters, numbers and single spaces.".
- Slugs (SOW-0015): the name with Latin, Greek and Cyrillic accents dropped (NFKD, U+0300–U+036F removed, then NFC again), lowercased, letters, marks and digits of any script kept, every other run of characters a single `-`; empty becomes `profile`. A clash gets `-2`, `-3`, … in creation order; `new` is reserved (it is the create route). The slug changes only when the name changes, so saving other fields never moves it. Migration 4 added the column and its unique index, and cleaned stored names that break the name rule (other characters become spaces, spaces collapse, empty becomes "Profile", a clash gets " 2", " 3"; valid names were kept first).
- `runs`, `jobs` and `applications` carry `profile_id NOT NULL REFERENCES profiles(id)`; proposals and status history belong to the profile of their application. Job dedupe is unique per profile (`UNIQUE (profile_id, dedupe_key)`), so the same posting can be stored once in each profile.
- Migration 3 replaced the single-row `profile` table: an existing profile became the first profile, named after its first target role (else "Default"), and owns every existing row; data without a profile went to a new profile named "Default"; an empty database gets no profile. The migration rebuilds the three tables with foreign keys off inside one transaction and aborts (rolls back) if `PRAGMA foreign_key_check` reports anything.
- API: `GET /api/profiles` lists profiles by name with `counts` (`jobs`, `applications`, `runs`); `POST /api/profiles` creates (201; 409 when the name is taken); `GET`/`PUT`/`DELETE /api/profiles/:pid`; `GET /api/profiles/by-slug/:slug` returns one profile for the UI's URLs (404 when no profile has that slug). Data routes stay keyed by id. Jobs, applications, proposals and runs live under `/api/profiles/:pid/{jobs,applications,proposals,runs}` with the same routes as before; an unknown profile is 404 "Profile not found", and an id that belongs to another profile is 404 as if it did not exist. `/api/settings`, `/api/setup/*`, `/api/health` and `DELETE /api/runs/logs` stay global. The old `/api/profile` route is gone.
- `DELETE /api/profiles/:pid` is refused with 409 "This profile has a queued or running run; cancel it first"; otherwise it deletes the profile with its runs, jobs, applications, proposals and status history in one transaction (204) and then removes those runs' log files and run directories. The agent never sees the profile name; prompts are unchanged.

## Agent integration

- The app never calls a model. It spawns the user's agent CLI (`claude`, `codex`, or a custom command) without a shell. The `custom` adapter is always offered in Setup; `check()` reports installed/version and, for the `claude` and `codex` presets, a sign-in state from `claude auth status` / `codex login status` (exit 0 = signed in, non-zero = not signed in with the first output line, probe failure or timeout = unknown); custom has no probe. A run is refused with 422 when the selected agent is not installed or the custom command is invalid.
- Timeouts and aborts kill the agent's whole process group on POSIX and the process tree on Windows. On Windows the command is resolved through `PATH` and `PATHEXT`, and an npm `.cmd` shim is started as `node <cli.js>` without a shell; this is tested with simulated shims only, not on a real Windows machine.
- Two task kinds: `discover_jobs`, `sync_mail`. Each has a versioned prompt template and a JSON output schema the agent must satisfy. The schema given to the agent is strict: no `$schema` pointer, no `default` keywords, `additionalProperties: false` on every object, every property required (so agents emit empty strings and nulls explicitly). The app's own parse of the agent output still applies defaults for missing optional fields.
- Every prompt states: read only; never apply; never send, draft or label mail.
- The discovery prompt (v4; v3 from SOW-0016, v4 from SOW-0017) carries a `{{scope}}` section (all sources, ATS first, for a Default run; one source family per Max worker), steps (short title-variant searches with the scope's job board host; search before opening; prefer ATS and careers-page links; when the agent can fetch pages, read a Greenhouse `boards-api.greenhouse.io/v1/boards/<board>/jobs` or Lever `api.lever.co/v0/postings/<company>?mode=json` list once instead of single postings; never fetch Ashby's list, which is several MB, and open each Ashby posting once before returning it, dropping any that fails to load, because search results keep closed Ashby postings; never open aggregator pages to confirm a job) and a budget: about 10 minutes, at most 30 jobs, stop at about 10 strong matches, fewer is fine and never pad, open at most one page per job, no subagents, the app verifies links itself. Each job carries `checks.location`, `checks.remote` and `checks.seniority` (`pass`, `fail` or `unknown`; `pass` when the profile leaves the field open). The default run timeout is 20 minutes (`run_timeout_ms` 1200000), editable in Settings between 10 seconds and 1 hour; every Max worker gets the same timeout.
- The Claude Code preset runs `claude -p` with `--setting-sources user` (user-level settings, credentials, plugins and claude.ai connectors; project settings implied by the run cwd are skipped), `--settings` with `claudeMdExcludes: ["**/CLAUDE.md"]`, `disableAllHooks: true` and `autoMemoryEnabled: false` for both run kinds (SOW-0018: the user's personal CLAUDE.md, auto-memory and hooks stay out of app runs) and `--disallowedTools Agent,Task` (no subagents), plus the permission mode and allowed tools from Settings. Discovery runs also get (SOW-0016): `--tools` with the built-in tool names from `allowed_tools_discover` (permission rules such as `Bash(curl:*)` cut to the name; omitted when there are none), `--strict-mcp-config` unless an allowed discovery tool starts with `mcp__` (user-level MCP servers cost about 260k context tokens per run on a machine with many connectors, measured 2026-11-07), and `--max-budget-usd <claude_max_budget_usd_discover>` when that setting is non-empty (default `5`; API pattern `^\d{1,4}(\.\d{1,2})?$`, more than 0, re-checked in the preset). The cap is Claude Code's own list-price estimate; reaching it ends the agent with no structured output.
- The Codex preset passes `--disable multi_agent` for both kinds (sub-agents are on by default in codex-cli 0.163) and, for discovery, `-c web_search="live"` (the default `cached` reads an OpenAI index without live web access).
- Model and effort (SOW-0011): Settings holds `<agent>_model_<kind>` and `<agent>_effort_<kind>` for `claude` and `codex` and the kinds `discover` and `sync` (8 keys, default `''`). `''` means the agent's own default and adds no flag; the app does not read the CLIs' config files to guess that default. Claude gets `--model <m>` / `--effort <e>`; Codex gets `-m <m>` / `-c model_reasoning_effort="<e>"`. A custom command carries its own flags. The API accepts a model matching `^[A-Za-z0-9][A-Za-z0-9._:/[\]-]{0,99}$` and an effort matching `^[a-z]{1,20}$` (or `''`); the preset re-checks stored values because they reach argv. Every effort level is allowed; the UI warns on `xhigh`, `max` and `ultra` (Codex `ultra` delegates to subagents).
- `GET /api/setup/models` returns `{ claude, codex }`, each `{ source: 'static' | 'agent' | 'unavailable', models: [{ id, label, efforts }], efforts }`. Claude is a static list (`fable`, `opus`, `sonnet`; efforts low to max, from `claude --help`). Codex comes from `codex debug models` (5 s timeout, hidden models skipped); any failure gives `unavailable` and the UI falls back to free text.
- `sync_mail` output carries a required `mail_access` boolean. `false` fails the run with "Your agent has no Gmail tool".

## Status pipeline

`saved`, `applied`, `screening`, `interview`, `offer`, `rejected`, `withdrawn`, `no_response`.

- `saved` has no applied date and is excluded from mail sync.
- `no_response` is user-set only.
- Save and Mark applied on a job are idempotent: they return the existing application for that job, advancing `saved` to `applied` when asked; manual applications infer `sender_domains` from their URL.
- `GET /api/profiles/:pid/jobs` items are `JobListItem`: the job row plus `application_status`, the status of the latest application linked to that job (`null` when none). The Jobs page derives its Saved/Applied/Interview… badge and its Save and Mark applied buttons from this field, so the state survives reloads.
- Status changes from mail are proposals; nothing changes until the user accepts one. Every change is recorded in `status_history` with source `user` or `proposal`.

## Discovery results

- Every returned URL is canonicalised and verified: `ok`, `redirected`, `dead` (404, 410, DNS failure, connection refused, or a `greenhouse.io` URL carrying `error=true`, as a redirect hop or as the returned URL itself, which is how Greenhouse answers a closed or unknown job id), `unverified` (403, 429, 999, 5xx, timeout, redirect loop).
- `jobs.fit_checks` (migration 5) stores the agent's `checks` as JSON; older jobs have NULL. A value that does not parse reads as null.
- `dead` jobs are stored but hidden by default; `unverified` jobs are shown with a badge.
- Dedupe key is the canonical URL, else normalised `company|title|location`; dedupe and the known URLs handed to the agent are per profile.

## Runs

- Statuses `queued`, `running`, `succeeded`, `failed`, `aborted`. One run at a time across all profiles (one global queue). One active run per profile and kind, not counting a run that is being cancelled: starting a run of that kind (button or schedule) queues a new run behind it instead of returning the dying one (SOW-0012). Each run belongs to the profile it was started for; discovery uses that profile, and mail sync checks only that profile's open applications and its own reviewed message ids (SOW-0014).
- Each run keeps a full log under `runs/<id>.log` and its prompt/schema/output files under `runs/<id>/`; the log is streamed to the UI over SSE. "Purge run logs" deletes both for every run that is not active.
- `runs.started_at` and `runs.prompt_version` are null until set; `runs.adapter_id` records the adapter used.
- `runs.agent_model` and `runs.agent_effort` (migration 2) record what the run asked for: `''` = agent default, NULL = not recorded (older run, custom command, or the run never reached the agent). `runs.agent_model_reported` holds the model Claude Code names in its stream-json init event; Codex `--json` reports neither model nor effort, and no agent reports the effort. Handlers write these through `RunContext.recordAgent` before the agent starts and after it returns, so failed and aborted runs keep them; a write failure is logged and never fails the run.
- `runs.effort_mode` (migration 5) is `default` or `max`; sync runs are always `default`. `runs.usage_cost_usd`, `usage_input_tokens` and `usage_output_tokens` hold what the agent reported, summed over Max workers, NULL when nothing was reported: Claude from its last `result` event (`total_cost_usd`; tokens from `modelUsage`, input including cache reads and writes), Codex from its last `turn.completed.usage` (a running total, so the last event is the run's usage; no cost). Handlers write them through `RunContext.recordUsage`, also when the run fails. Only discovery records usage, so the Run page shows Mode and Usage for discovery runs only. An agent that is killed (timeout, cancel) never writes its final event and reports nothing.
- Runs left `running` by a crash are marked `aborted` with reason "server restarted" on next start.
- Cancel (SOW-0012): `POST /api/profiles/:pid/runs/:id/cancel`. A queued run is recorded `aborted` / "Cancelled by user" at once and never starts (202). A running run whose agent is still working is aborted: the agent's process tree is killed and the run ends `aborted` / "Cancelled by user" (202 returns the run while it is still `running`; it ends within about 6 s). Once the handler calls `beginSaving()` (discovery: after a valid agent result, before link checks; mail sync: after the mail source returns, before proposals are created) the queue logs "Saving results; the run can no longer be cancelled" and cancel returns 409; a cancel that arrived first makes `beginSaving()` throw so nothing is saved. Finished runs return 409, unknown ids 404. Shutdown still records "Aborted"; a cancel during shutdown keeps "Aborted", and a run cancelled before shutdown keeps "Cancelled by user" even if shutdown gives up waiting.

## Discovery effort levels (SOW-0016)

- `POST /api/profiles/:pid/runs/discover` takes an optional JSON body `{ "mode": "default" | "max" }` (strict; no body means `default`; a body that is not JSON is 415). When a discovery of the profile is already queued or running, the same mode returns that run (202) and the other mode is refused with 409 "A discovery run is already active".
- Default: one agent process with the full scope.
- Max: five agent processes by source family, in order Greenhouse, Lever, Ashby, other ATS and careers pages, remote and niche boards (`MAX_EFFORT_SOURCES`), at most three at a time (`MAX_EFFORT_CONCURRENCY`). Each worker has its own directory `runs/<id>/worker-<n>/`, the run timeout, the run's abort signal and, on Claude, its own spend cap. Worker output lines are logged with a `[worker <n>] ` prefix. Results go through the same canonicalise, verify and dedupe path. A worker never rejects: an error outside the agent call (for example a log write) counts as that worker failing, so the run never ends while other workers' agents still run. After a cancel, workers still waiting for a slot do not start. Failed workers are logged as "Worker <n> (<source>) failed: <error>" and the summary ends with "; <k> of 5 workers failed"; the run fails only when every worker fails, with the first worker's error. Claude Code's WebSearch treats `site:` as a hint (probed 2026-11-07), so workers on Claude overlap and dedupe removes the repeats.
- Max is manual only; the scheduler never starts discovery.

## Scheduled sync

Optional interval (`off`, `1h`, `6h`, `24h`) shared by all profiles. On each tick it enqueues one `sync_mail` per profile that has open applications while the server runs; profiles without open applications are skipped. No OS scheduler.

## User interface

- The SPA under `src/ui/` is built from shadcn/ui components (Tailwind CSS v4, Radix primitives, lucide icons), owned as source under `src/ui/components/ui/` (SOW-0010). Desktop browsers only; Tailwind v4 needs Chrome 111+, Safari 16.4+ or Firefox 128+.
- Routes (SOW-0014): `/` is the profiles screen (cards with name, target roles, counts, Open, Edit and Delete, plus New profile); with no profile it shows the profile form ("Create your first profile"). `/profiles/new` creates one; `/profiles/:profileSlug` is that profile's Dashboard and `/profiles/:profileSlug/{jobs,applications,applications/:id,review,runs,runs/:id,profile}` its pages. The shell resolves the slug once (non-ASCII slugs are percent-encoded in the URL); an unknown slug shows "Profile not found" with a link back to the profiles screen; renaming a profile on its edit page moves to the new slug, and old URLs of a renamed profile show "Profile not found". `/settings` and `/setup` are global. Any other path, including the old `/jobs`-style routes, redirects to `/`. The startup check still sends the user to `/setup` when the chosen agent is not installed.
- A fixed left sidebar holds navigation and a theme menu. On the profiles screen its header shows "Job Tracker" and it lists Profiles and Settings. Inside a profile the header is a link "← <profile name>" back to the profiles screen (cut with an ellipsis to the sidebar width, full name on hover), followed by Dashboard, Jobs, Applications, Review (with that profile's pending-proposal count), Runs and Profile, then Settings. The count is re-read on navigation; the name updates as soon as the profile is saved. The theme menu offers Light, Dark and System; the choice is stored in browser `localStorage` under `theme` (default System, which follows the OS setting live); a pre-paint script in `index.html` applies it before first render.
- The Dashboard and the Jobs page each have one "Find jobs" split button (SOW-0020, shadcn Button Group with a dropdown menu): the arrow ("Choose search mode") opens a radio menu with Default ("One agent. Balances results and tokens.") and Max effort ("Five agents, one per source. Several times the tokens; asks before it starts."). Choosing an item only changes the selection; the main button then reads "Find jobs" (search icon) or "Find jobs with max effort" (rocket icon). The selection is not stored and every page load starts on Default. On the Dashboard both parts are turned off while a run is starting, like the other Dashboard run buttons. In Default the main button starts a run at once; in Max effort it opens a confirmation dialog that loads the settings and the profile's last 50 runs and states: the five sources and the three-at-a-time limit, the per-worker time limit in minutes, that it runs on the user's own agent plan and can use up its limits, the Claude per-worker cap (or that no cap applies for an empty setting, Codex or a custom command), and what the last Max run with recorded usage reported, noting that a search that times out or is cancelled reports nothing. No dollar estimate is shown up front. Nothing starts until the user confirms; a 409 is shown above the list.
- The Jobs table has a Fit column with Location, Remote and Seniority badges (✓ pass, ✗ fail, ? unknown, with an `aria-label` such as "Remote: does not match"); jobs without verdicts show a dash. Verdicts never hide a job.
- Settings → Runs has "Claude spend cap per discovery agent (USD)" (empty = no cap).
- Destructive actions confirm first: "Purge run logs" (Settings), "Dismiss" (Jobs), "Cancel run" (Run page, Runs list) and "Delete" on a profile card (naming the jobs, applications and runs that go with it) open a confirmation dialog and do nothing when dismissed.
- Queued and running runs show "Cancel run" on the Run page and on their Runs list row. After a cancel request the Run page shows "Cancelling…" until the run ends; once the run logs its saving line it shows "Saving results…" (disabled). The Runs list re-reads the list each second (up to 30 s) until the cancelled run has ended; a refused cancel (409) is shown above the list and the list is re-read once. The saving line is matched exactly (`RUN_SAVING_LOG_LINE` in `domain/types.ts`), so agent output cannot lock the control.
- The profile form shows "Letters, numbers and spaces only." under Name; while the name breaks the rule it shows "Use only letters, numbers and single spaces." there instead (`aria-invalid`) and does not submit.
- Manual applications are added from an "Add application" side sheet on the Applications screen; the sheet closes after a successful add.
- Feedback stays inline: errors render with `role="alert"`, success messages ("Saved") with `role="status"`, next to the action that produced them. No toasts.
- Settings → Agent shows model and effort per run kind for the selected claude or codex agent (saved with the Agent section; model is free text with suggestions, effort a select with "Agent default" and the levels the chosen model supports when the catalog knows it). The Run page shows agent, model (plus "ran as" when reported), effort, the discovery mode (Default or Max effort) and Usage (for example "$1.23 estimated · 1.3M tokens in, 3.4k out", or "Not reported"); the Dashboard has an Agent card with the saved choice per run kind.
- The Run page log is readable by default (SOW-0013): `src/ui/log-format.ts` turns each stored line into a row with an icon. Claude stream-json and Codex `--json` events become short messages (agent text capped at 300 characters, one line per web search, page fetch, Gmail call, command or other tool, tool errors, start with the model, finish with duration/cost or tokens and what was returned). Hooks, `rate_limit_event` with status `allowed`, thinking/reasoning, successful tool results, text inside `user` events, `ToolSearch`/`TodoWrite`/`StructuredOutput`, and unknown agent event types are hidden. Codex web searches are shown from the completed item (Codex fills in the query and action only then; `open_page`/`find_in_page` read "Opening <url>"). App lines (queue and handler messages) and `[stderr] ` lines are muted; failed/aborted run lines and errors are highlighted; other plain lines are shown as text, and JSON without a `type` that carries `jobs` or `findings` is summarised as "Agent returned N …". Every row is capped at 300 characters. Max worker lines (`[worker <n>] …`) are formatted like any other line and labelled "Worker <n>: …", with Codex steps paired per worker; "Max effort: …" and "Worker <n> (…) started" are app lines and a failed worker is a warning. A "Show raw output" checkbox shows the stored lines unchanged. The log file, the log endpoint and the SSE stream are unchanged.
- Selects are native `<select>` elements (shadcn `NativeSelect`) so keyboard behaviour and form tests stay native.
- No network fonts or CDN assets: the UI uses the system font stack and ships fully in `dist/ui`.
